реального продавца; сейчас его **НЕ ВЫПОЛНЯТЬ**. Запуск разрешается только после отдельного решения

Ни один шаг здесь не может быть отмечён выполненным агентом. Автоматические проверки (Vitest,
Playwright, constitution CI) гоняются против репозитория и уже зелёные — этот документ про то,
чего они не проверяют и проверить не могут: настоящий сервер, настоящую почту, настоящую
доставку в Telegram, настоящий браузер.

Инвентаризационный anchor: `origin/master` `9647ebed61796b233019ca9042050dc45d520c16` (после PR #312).
Перед будущим выполнением обязательно заново подтвердить текущий master и GREEN CI; этот anchor не
является разрешением на запуск и не доказывает готовность продукта или окружения.

Правило: **любой FAIL останавливает запуск.** Не «поправим после подключения продавца».

## 1. Переменные окружения

Создать `.env` **рядом с `docker-compose.yml`** (не путать с `backend/.env` — это dev-файл, в
контейнер он не попадает).

```bash
POSTGRES_PASSWORD=$(openssl rand -hex 24)
SECRET_KEY=$(openssl rand -hex 32)
CRED_ENC_KEY=$(python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())")

SMTP_HOST=<хост почты>
SMTP_PORT=587
SMTP_USER=<логин>
SMTP_PASSWORD=<пароль>
SMTP_FROM=<адрес отправителя>

FRONTEND_URL=https://<домен фронтенда>          # точный origin, без слэша в конце
NEXT_PUBLIC_API_URL=https://<домен бэкенда>     # вшивается в бандл ПРИ СБОРКЕ

TELEGRAM_BOT_TOKEN=<токен от @BotFather>
```

Проверка:

```bash
docker compose config >/dev/null && echo COMPOSE_OK
```

**PASS:** печатается `COMPOSE_OK`.
**FAIL:** compose ругается на незаданную переменную (`POSTGRES_PASSWORD`, `SECRET_KEY`,
`CRED_ENC_KEY`, `SMTP_HOST`, `TELEGRAM_BOT_TOKEN`). Это не баг, это защита: заполнить и повторить.

> `FRONTEND_URL` и `NEXT_PUBLIC_API_URL` имеют dev-дефолты `localhost`, но ведут себя по-разному.
> В `APP_ENV=production` localhost в `FRONTEND_URL` **останавливает запуск backend fail-fast** — ссылки
> верификации/сброса иначе были бы нерабочими. `NEXT_PUBLIC_API_URL` вшивается во frontend при сборке
> и сам по себе запуск не останавливает: забытый build arg оставит браузер на `localhost:8000`.
> Оба значения проверяются отдельно на шагах 6 и 5.

Отдельно: `AUTOMATION_ENABLED` **не задавать**. Дефолт `false` (`backend/config.py:82`) —
маркетплейс-автодействия должны остаться выключенными. `NEXT_PUBLIC_GROWTH_CONTOUR` **не
задавать**: значение `1` вернёт в интерфейс незаконченные разделы.

## 2. Сборка и первый запуск

```bash
docker compose build --no-cache
docker compose up -d
docker compose ps
```

**PASS:** `postgres` — `healthy`, `backend` и `frontend` — `running`, ни один не в рестарт-петле.
**FAIL:** `backend` перезапускается. Смотреть причину:

```bash
docker compose logs backend | tail -40
```

Ожидаемые сообщения при неверном конфиге (это **правильное** поведение, fail-closed):
`[ПУЛЬТ] Startup aborted. Fix production config errors:` — далее список. Исправить и повторить.

## 3. База данных и миграции

```bash
docker compose exec backend alembic heads
docker compose exec backend alembic current
```

**PASS:** `heads` печатает **ровно одну** строку; `current` совпадает с ней и помечен `(head)`.
**FAIL:** голов больше одной, либо `current` отстаёт от `heads`. Не запускать продавца.

Миграции применяются автоматически при старте контейнера (`backend/Dockerfile:13`:
`alembic upgrade head && uvicorn …`), в **одном** процессе — гонки нет.

> **Не масштабировать бэкенд** (`docker compose up --scale backend=N`): несколько контейнеров
> начнут применять миграции одновременно. Один бэкенд — обязательное условие этой конфигурации.

Порт Postgres наружу не опубликован. Если нужен доступ для администрирования — раскомментировать
в `docker-compose.yml` `"127.0.0.1:5432:5432"`: тогда база доступна с самого хоста (psql, туннель)
и **ни с одной другой машины в сети**.

## 4. Продакшен-безопасность (до первого продавца)

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<домен бэкенда>/docs
curl -s -o /dev/null -w "%{http_code}\n" https://<домен бэкенда>/openapi.json
```

**PASS:** оба — `404`.
**FAIL:** `200`. Значит `APP_ENV` не равен ровно `production` (`backend/main.py:84`). Это же
означает, что **весь блок продакшен-проверок пропущен** — конфигурация небезопасна целиком.

```bash
docker compose exec postgres sh -c 'nc -z -w2 postgres 5432 && echo internal_ok'
```

**PASS:** `internal_ok` (бэкенд ходит в базу по внутренней сети).

С **другой** машины в той же сети:

```bash
nc -z -w2 <ip хоста> 5432 ; echo "exit=$?"
nc -z -w2 <ip хоста> 6379 ; echo "exit=$?"
```

**PASS:** оба `exit=1` — порты закрыты. Redis из развёртывания удалён совсем.
**FAIL:** любой порт отвечает. Не запускать продавца.

**PASS:** запросы уходят на `https://<домен бэкенда>`.
**FAIL:** в запросах виден `localhost:8000`. Значит `NEXT_PUBLIC_API_URL` не был задан **при

## 6. Настоящая почта (продавец A)

1. Открыть `https://<домен фронтенда>/register`, зарегистрироваться на ящик продавца **A**.
2. В DevTools → Network открыть ответ `POST /api/auth/register`.

**PASS:** тело ответа — только `{"message": "..."}`. **Токена в ответе нет.**
**FAIL:** в ответе есть `token` или ссылка. Немедленный стоп — это дыра захвата аккаунта.

3. Попробовать войти **до** подтверждения почты.

**PASS:** вход отклонён с текстом «Подтвердите email перед входом».
**FAIL:** вход прошёл.

4. Дождаться письма (проверить и «Спам»).

**PASS:** письмо пришло, ссылка ведёт на `https://<домен фронтенда>/verify-email?token=…`.
**FAIL:** письма нет. Смотреть `docker compose logs backend | grep -i email`. Если видно
`email_send_failed` — неверные SMTP-креды: регистрация вернёт 200, а воронка мертва.

5. Открыть ссылку, затем войти.

**PASS:** вход прошёл, открылся `/dashboard`.

6. Проверить сброс пароля: `/forgot-password` → письмо приходит → ссылка работает.

7. Проверить, что токены нигде не светятся:

```bash
docker compose logs backend | grep -iE "verify-email\?token=|verification_token|reset_token"
```

**PASS:** пусто.
**FAIL:** токен в логах. Это происходит, только если `SMTP_HOST` не задан (`services/email.py:46`)
— но тогда бэкенд не должен был стартовать. Разбираться до запуска.

Также: в DevTools → Console на `/register` и `/verify-email` не должно быть ни токена, ни
секретов. **PASS:** консоль чиста.

**FAIL:** видны любые метрики или карточки — у нового продавца данных нет, показывать нечего.

## 8. Telegram (продавец A)

Telegram **входит в первый релиз**, поэтому его проверка обязательна.

1. Убедиться, что токен дошёл до процесса:

```bash
docker compose exec backend sh -c 'test -n "$TELEGRAM_BOT_TOKEN" && echo TOKEN_PRESENT || echo TOKEN_MISSING'
```

**PASS:** `TOKEN_PRESENT`. Значение **не печатать**.
**FAIL:** `TOKEN_MISSING` — но тогда бэкенд не должен был стартовать (compose требует переменную).

2. В Telegram написать `/start` боту `@userinfobot`, получить свой Chat ID.
3. «Настройки» → «Подключить Telegram» → вставить Chat ID → «Сохранить».
4. Нажать **«Тест»**.

**PASS:** сообщение от бота реально пришло в Telegram, на кнопке — «Отправлено».
**FAIL:** «Ошибка» или сообщение не пришло. **Это блокер запуска:** интерфейс предлагает Telegram
как работающий. Либо чинить доставку, либо не запускаться.

5. «Аккаунт» → Intelligence Loop → «Проверить сейчас».

**PASS:** кнопка отвечает «Новых нет» (если инсайтов пока нет) или «Отправлено N», и при N > 0
сообщения действительно приходят.
**FAIL:** «Ошибка».

6. Секреты в логах:

```bash
docker compose logs backend | grep -iE "bot[0-9]{6,}|TELEGRAM_BOT_TOKEN"
```

**PASS:** пусто.

## 9. 2FA (продавец A, в настоящем браузере)

1. «Аккаунт» → «Безопасность» → открыть DevTools → вкладка Network → **очистить** → нажать
   «Включить 2FA».

**PASS:** в Network **нет ни одного запроса к стороннему хосту**. В частности — ничего к
`api.qrserver.com`. Единственный запрос — `POST /api/auth/mfa/setup` к своему бэкенду.
**FAIL (жёсткий):** любой внешний запрос, в URL которого есть `otpauth` или секрет. Стоп.

2. Правый клик по QR → «Просмотреть код».

**PASS:** это инлайновый `<svg>` с `<path>`. Не `<img>`.

3. Отсканировать QR в Google Authenticator / Aegis, ввести 6-значный код → «Подтвердить».

**PASS:** 2FA включилась, статус «✓ Включено».

4. Проверить запасной путь: включить 2FA заново и **вручную** ввести показанный ключ в приложение.

**PASS:** ключ виден, копируется, приложение принимает его и выдаёт рабочие коды.

5. Выйти и войти заново.

**PASS:** после пароля запрашивается код из приложения; с верным кодом вход проходит, с неверным —
нет.

6. Отключить 2FA (нужен действующий код).

**PASS:** отключилась, статус «Выключено».

7. Секрет в логах:

```bash
docker compose logs backend | grep -iE "otpauth|secret="
```

**PASS:** пусто.

## 10. Изоляция между продавцами (продавец B)

Зарегистрировать **второго** продавца B на другой ящик, подтвердить почту, войти.

1. У продавца B **не загружать ничего**.

**PASS:** на главной у B — «Нет данных для анализа». **Ни одной** карточки, ни одного числа
продавца A.
**FAIL (жёсткий):** B видит данные A. Немедленный стоп, продавцов не подключать.

2. Взять `import_id` продавца A (DevTools → Network на странице импорта у A) и, будучи
   залогиненным как **B**, запросить его напрямую:

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer <токен продавца B>" \
  https://<домен бэкенда>/api/import/<import_id продавца A>/confirm -X POST
```

**PASS:** `404`.
**FAIL:** `200` или чужие данные в ответе. Стоп.

3. Убедиться, что ошибки не выдают внутренностей: в ответах на неверные запросы нет трейсбеков,
   SQL и имён таблиц.

**PASS:** только человекочитаемое сообщение.

## 12. Критерии отката

Откатывать **немедленно**, не дожидаясь конца чек-листа, если:

- продавец видит числа, товары или карточки, которых нет в его загруженном отчёте;
- продавец видит данные другого продавца;
- токен верификации или сброса пароля обнаружен в ответе API, в логах или в консоли браузера;
- при включении 2FA уходит запрос к стороннему хосту;
- `/docs` или `/openapi.json` отвечают `200`;
- порт базы данных отвечает с другой машины;
- Telegram подан как работающий, но сообщения не доходят;
- бэкенд в рестарт-петле или `alembic heads` показывает больше одной головы.

Как откатывать:

```bash
docker compose down                 # данные в томе postgres_data сохраняются
git checkout <предыдущий тег>
docker compose build --no-cache && docker compose up -d
```

Миграции вперёд не откатываются автоматически. Если релиз добавил миграцию и её нужно снять —
делать это **вручную и осознанно** (`alembic downgrade -1`), предварительно сняв дамп:

```bash
docker compose exec postgres pg_dump -U postgres business_pult > backup-$(date +%F-%H%M).sql
```
